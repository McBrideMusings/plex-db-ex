# Roadmap

Tracked on [the issue backlog](https://github.com/McBrideMusings/plex-db-ex/issues); this page is
the shape, the issues are the work.

## Now

Milestone: **Identity and enrichment**. Nothing downstream is trustworthy until the two `item_id`
implementations agree on real data — [#5](https://github.com/McBrideMusings/plex-db-ex/issues/5) is
the measurement that proves it, and the reason the rest of this milestone exists.

- [x] [#18](https://github.com/McBrideMusings/plex-db-ex/issues/18) Treat an empty GUID value as absent
- [x] [#15](https://github.com/McBrideMusings/plex-db-ex/issues/15) Publish a read-only snapshot for consumers
- [x] [#16](https://github.com/McBrideMusings/plex-db-ex/issues/16) Set the busy timeout explicitly instead of inheriting it
- [x] [#3](https://github.com/McBrideMusings/plex-db-ex/issues/3) Walk the Plex library into items and external ids

## Open questions

Tracked as `question` issues — decisions, never implemented from.

- [x] [#13](https://github.com/McBrideMusings/plex-db-ex/issues/13) Who owns the Layer 2 ranking knobs? Answered against real vectors over 25,835 plays: the half-life and the negative weight are not knobs (decay concentrates rather than mixes; abandonment is no signal, not negative signal), and the exploration fraction belongs to a channel, not to this store. The rollup ships no knobs to own — [ADR-0011](./adr/0011-a-taste-vector-weights-a-season-not-an-episode), implemented by [#32](https://github.com/McBrideMusings/plex-db-ex/issues/32).
- [x] [#14](https://github.com/McBrideMusings/plex-db-ex/issues/14) Obtain a working Trakt client id — closed, not answerable. The inherited id was a real, formerly working one; Trakt deleted existing API applications without notice around 1–2 August 2026 and gated new ones behind VIP, calling it temporary with no date. Nothing is built from it now that #12 and #36 are dropped. (`403` from Trakt means "invalid API key or unapproved app" — not a VIP gate, which is `426`.)
- [ ] [#17](https://github.com/McBrideMusings/plex-db-ex/issues/17) Should an empty GUID value be treated as absent? Changes what an `item_id` is, so it must land in both repos at once.

## Later

**Running it unattended.** The store's sources and its consumer are both on the Unraid host; the
Mac is in the path only because that is where the code was written.

- [x] [#45](https://github.com/McBrideMusings/plex-db-ex/issues/45) `plexdb sweep` — one command runs the whole pass, each step declaring whether its failure ends the run ([ADR-0014](./adr/0014-the-sweep-is-a-command-not-a-shell-script))
- [x] [#43](https://github.com/McBrideMusings/plex-db-ex/issues/43) A container image whose entrypoint loops on a wall-clock schedule, so two sweeps cannot overlap
- [x] [#47](https://github.com/McBrideMusings/plex-db-ex/issues/47) Installed on the host and running unattended: `plays` 25,880 and `enrichment` 132,341 after the first container sweep, the snapshot published to the station's own directory, and no run-config drift between the live container and `[docker_run]`
- [x] [#59](https://github.com/McBrideMusings/plex-db-ex/issues/59) `plexdb check` — ask a store how it is without changing it: schema version against the running build, `quick_check`, row counts, how old the newest play, enrichment row and id-seen stamp are, the identities more than one rating key points at, the `fs:` count, the backups. Read-only, so `admin host-exec check` answers it against the live store mid-sweep instead of a 130 MB round trip; non-zero when the store is behind or damaged
- [x] [#48](https://github.com/McBrideMusings/plex-db-ex/issues/48) Plex collections are not harvested at all. The pairwise `local_collection` edge shape wrote 17.8M rows and a 3.7 GB snapshot; rather than reshape it, the source was dropped — a collection assembled by hand is a similarity its author already knows about, so feeding it back as a recommendation signal is circular

- [x] [#34](https://github.com/McBrideMusings/plex-db-ex/issues/34) MDBList crowd lists — schema v6's `collection` and `collection_membership`, filled by `plexdb harvest-mdblist`. Measured on the author's library: 50 lists, 11,896 memberships, 15,237 entries dropped as outside it
- [x] [#46](https://github.com/McBrideMusings/plex-db-ex/issues/46) The Gated Source contract — a source declares its client, its key and its write; the credential check, the derived staleness window and the two flags stop being copied per source
- [ ] The rest of the crowd-list sources, one at a time, each a new `source` value rather than a schema change (Letterboxd is done): [#37](https://github.com/McBrideMusings/plex-db-ex/issues/37) editorial/RSS, [#38](https://github.com/McBrideMusings/plex-db-ex/issues/38) Reddit. [#36](https://github.com/McBrideMusings/plex-db-ex/issues/36) Trakt is dropped for the same reason as #12
- [x] Crowd-list discovery spike (beads `plex-db-ex-k1q.3`), probed 2026-10-15 from the plexdb image: MDBList `GET /lists/search?query=` answers 200 (name match only, 100 lists per call, `limit`/`offset` page, 1 quota unit per call) and a Letterboxd list page `/<user>/list/<slug>/` answers 200 with 100 entries per page and `/page/N/` pagination; Letterboxd `/film/<slug>/lists/` (and its pages) answers a Cloudflare 403 challenge, so "lists containing this film" has no keyless route
- [x] [#29](https://github.com/McBrideMusings/plex-db-ex/issues/29) The reader crate's collection-membership accessor — `Reader::collections_for(item_id)` joins `collection_membership` with `collection`, every source-nullable field staying `Option<_>`
- [x] Plex DB-EX (beads epic `plex-db-ex-7tm`) — a read-only browser view over `tmdb_keywords`, to find tags that describe packaging rather than subject (`duringcreditsstinger` tags 383 movies and travels with `superhero`). `plexdb explore` ships the tag table and the titles-tagged-X drill-down, and the container serves it over the snapshot on the one host address `PLEXDB_EXPLORE_BIND` names. A Graph view draws the tags that share the most titles with one tag, and a Title map view places every title by keyword similarity with the selected tag's titles highlighted. A Query tab runs one read-only SQL statement against the store (5 s and 500-row limits) with saved queries and recipes taken from the `plexdb-reader` accessors. One follow-up stays open: [plex-db-ex-0xo](https://github.com/McBrideMusings/plex-db-ex/issues/66) — whether a global keyword stoplist moves into this store, stays per-consumer (today's answer: the explorer's noise list lives in browser localStorage), or lives elsewhere
- [x] Related tags (Plex DB-EX) — selecting a tag opens Related tags and Titles tabs. Related tags ranks every tag that shares a title with it by a cautious lift (a Wilson lower bound, so pairings resting on two titles shrink), with an Evidence slider and a sortable Tag, Lift and Shared table; the tag table gains each tag's five most related tags, and `/api/cotags` serves the rows from the cached index. The Tag network lights related tags in four levels with spokes to the selected tag. Selecting two tags to see the titles that link them is open as the spike beads `plex-db-ex-jst`
- [x] Wikidata (beads `plex-db-ex-ka3.2`) — `plexdb enrich-wikidata`, the first keyless Gated Source: narrative location, set in period, main subject and genre as `source = 'wikidata'` keywords, `region` and `era` roles stated from the first two, and award received in an `awards` namespace. Measured on a pulled copy: 13,302 titles asked in 67 queries, 12,397 matched, 57,270 keywords, 2,246 role rows, 6,573 awards
- [x] AniList (beads `plex-db-ex-ka3.3`) — `plexdb enrich-anilist`: anime found through Fribb's `anime-list-full.json`, their AniList tags stored as `source = 'anilist'` keywords with AniList's 0–100 rank in `enrichment.rank` (the first writer of that column), spoiler tags under key `spoiler_keyword`, and `theme`, `era` and `character_trait` roles from tag categories. Measured on a pulled copy: 14,419 titles seen, 425 anime, 818 AniList ids in 17 requests (41 s), 7,590 keywords, 1,949 spoiler keywords, 280 role rows
- [x] Letterboxd themes (beads `plex-db-ex-ka3.4`) — `plexdb enrich-letterboxd`, a keyless scraper: each movie's film page reached through `/tmdb/<id>/`, its theme and mini-theme labels stored as unranked `source = 'letterboxd'` keywords, at most 1,000 movies per run, non-zero exit when more than 10% of film pages lose the film marker. Measured on a pulled copy: 50 movies in about 2 minutes, 46 with themes, 242 keywords, 0 parse failures; 11,674 movies have a TMDB id, so a first pass takes about 12 sweeps
- [x] MDBList ratings (beads `plex-db-ex-ka3.5`) — `plexdb enrich-mdblist-ratings`: every rating MDBList's batch title endpoint relays (IMDb, TMDB, Trakt, Letterboxd, Rotten Tomatoes critics and audience, Metacritic critics and users, RogerEbert, MyAnimeList), stored on each site's own scale in a `ratings` namespace with `<site>_votes` beside it, at most 100 requests per run. Measured on a pulled copy: 13,312 titles with an IMDb id in 68 requests (about 30 s), 94,844 ratings and 87,652 vote counts, 15 titles MDBList did not know
- [x] Lists tab (beads `plex-db-ex-k1q.4`) — Plex DB-EX shows every crowd list with its owned share, watched count, likes and fetch date, and one list's entries in rank order with the keywords its titles carry far more often than the library does. Read-only until `plex-db-ex-k1q.5`
- [x] Letterboxd crowd lists (beads `plex-db-ex-k1q.6`) — `plexdb harvest-letterboxd-lists` (sweep step 61, keyless) fetches the Letterboxd lists a person added by URL: every page of `/<user>/list/<list>/`, each film's TMDB id and type from its film page, written as `source = 'letterboxd'` collections, entries and memberships in the same per-list transaction as MDBList. A challenge, a page without the list marker, or fewer entries than the list states records a failed attempt and writes nothing
- [x] Outward list search (beads `plex-db-ex-k1q.7`) — `plexdb harvest-mdblist-search` (sweep step 62) asks MDBList's list search for each watched title and keeps the fetched candidates that hold at least `MDBLIST_SEARCH_MIN_TITLES` library titles, as `provenance = 'search'` with the count of watched titles in `seed_count`. MDBList matches list names only and has no lists-containing-a-title endpoint, so the name match is a lead and the threshold the filter. Measured on a pulled copy: 200 seeds asked gave 133 candidate lists; the first 20 fetched kept 12 and rejected 8 (1 to 3 library titles). Letterboxd's per-film list pages stay behind a Cloudflare challenge, so they are not used
- [x] Curate crowd lists (beads `plex-db-ex-k1q.5`) — the Lists tab and `plexdb list-decide <url> <added|excluded|refetch|retry|removed>` append to `list_decisions.json`; `plexdb fold-list-decisions` folds it into `list_decision` (schema v22) and `harvest-mdblist` acts on it: an excluded list is wiped and never fetched, an added MDBList URL is fetched with provenance `added`, a refetch ignores staleness once, a removed added list is dropped. A list whose fetch fails records `list_attempt` and the harvest goes on; three failures in a row stop it until a retry. `plexdb check` and the list table report failed lists ([ADR-0028](./adr/0028-list-decisions-and-fetch-attempts-are-keyed-by-list-url))
- [x] Roles tab (beads `plex-db-ex-ka3.7`) — Plex DB-EX lists keywords with every source's verdict per role and takes an accept or reject per (keyword, role) into `role_decisions.json`, which `plexdb fold-role-decisions` applies to `keyword_role_decisions` as the sweep step after `fold-merge-decisions`. The Merges tab's decisions file and the Roles tab's now share one implementation (`plexdb/decisions.py`)
- [x] Tag doctor (beads `plex-db-ex-c8j`) — Plex DB-EX's Doctor tab shows one title's keywords as a row per merge group and a column per source holding the raw spelling that source sent, with the judge or person that folded each one. A pinned card's closed "Sources and remapping" section lists the same rows and links each to its row in the tab. "Merge with…" searches the stored vocabulary and writes an accepted pair to `merge_decisions.json` through the Merges tab's route. Schema v18 lets the fold write a pair no judge was asked about. Decisions name raw spellings, resolved to stored values with the current `normalize_keyword` at read time, so a normalization migration does not orphan them (beads `plex-db-ex-odi`)
- [x] Display names (beads `plex-db-ex-pr7`, ADR-0021) — "Rename…" on a Doctor tab group, or beside either side of a Merges tab pair, gives a stored keyword a display name, written to `name_decisions.json` and folded into `keyword_names` (schema v19) by `plexdb fold-name-decisions`. Every Plex DB-EX label shows the name in place of the readable spelling, and a merge group with an unnamed head shows its newest member's name. Nothing that computes reads a name: the judges, embeddings, similarity, the map's vectors and the merge fold all use stored values and raw spellings
- [ ] Frame search (beads epic `plex-db-ex-8nb`, ADR-0022 to ADR-0026). A Frame index in its own `frames.db` (ADR-0024) holds one CLIP vector per Shot and one every 2 s inside longer Shots. It is filled during configured hours by `plexdb harvest-frames`, which reads each title's file from a read-only library mount (Plex names the file) and embeds through a configured OpenAI-compatible endpoint (ADR-0025). `search_shots` takes a phrase with optional negatives, weight and temperature, and a seeded `draw`; a Search tab in Plex DB-EX shows what a phrase returns, searching every indexed title when no pool is picked, and lists the Frame index's failures with Retry. Search only: no saved, accepted or rejected results. Measured on 20 films (35.9 hours): 447 Shots and 1.78 MB of int8 vectors per hour of video, so 110.9 GB for the 62,281-hour library; int8 keeps 9 of every 10 fp16 top-10 results, so `quant` stays int8; the harvester runs at 5.6× to 9.9× real time on 1080p with decoding most of the time, about 6,300 to 11,100 hours of decoding for the library on the CPU; `PLEXDB_FRAME_DECODE=cuda` decodes the scene scan on the GPU, which cuts 31% off a 4K HEVC film but only about 54 hours across the library, so decoding stays the cost (plex-db-ex-8nb.1.21). Tautulli logs no harvester read.
- [ ] Rust writer (beads epic `plex-db-ex-f58`, [ADR-0001](./adr/0001-one-writer-many-readers-sqlite-file-is-the-interface)) — the sweep steps move from Python to one Rust binary, `plexdb-rs` until the last slice renames it, a step at a time; both take the same writer lock. `plexdb steps --json` lists which implementation runs each step, and `admin parity <step>` runs both on two copies of a pulled store and lists every row they wrote differently. `fold-list-decisions` runs in Rust: zero differing rows over 1,778,221 compared on the 2026-10-23 store (plex-db-ex-f58.2). The schema and `plexdb migrate` are Rust's (`crates/plexdb-schema`, plex-db-ex-f58.3): migrating copies at v17, v18 and v22 and a store built from nothing wrote zero rows differently from the Python chain, and Python's tests build their stores with it. Keyword normalization is Rust's too (`crates/plexdb-keywords`, held to `tests/fixtures/keyword_normalization.json`, 82,520 Python outputs, with zero mismatches), and with it the other three folds, the three TMDB enrichers, and migrating a store below v17 that holds keywords (plex-db-ex-f58.5) The crowd-list harvests and list commands run in Rust too (`harvest-mdblist`, `harvest-letterboxd-lists`, `harvest-mdblist-search`, `lists`, `list`, `list-decide`; plex-db-ex-f58.7): zero differing rows, identical printed lines, identical decisions files and identical request sequences against a recorded MDBList and Letterboxd (`tools/fake_lists.py`), because two live runs cannot be compared and a real one spends the daily MDBList quota. `prune-keyword-verdicts`, `film-suffix-verdicts`, `judge-keyword-pairs` and `judge-keyword-roles` run in Rust (plex-db-ex-f58.8): zero differing rows, identical printed lines and identical request sequences (judge steps against a recorded embedding server and Jev, `tools/parity_fakes.py`), on an aged copy of the 2026-10-26 store. The Rust embedding cache is `keyword-embeddings.bin`, so the first Rust sweep embeds the vocabulary once more. `plexdb frames migrate|status|queue` run in Rust (plex-db-ex-f58.10, first part): zero differing rows in `frames.db` and the store, and identical `status` output, on a seeded Frame index; `latent-users` runs in Rust (plex-db-ex-f58.16): zero differing rows over 1,780,346 compared and identical printed lines against a recorded `/accounts` (`tools/parity_fakes.py`). `harvest-frames`, `record-panels`, `frames probe-encoder` and `quant-agreement` still run in Python.
